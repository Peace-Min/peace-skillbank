# XML 구조 분석 보고서 스킬

임의의 XML을 분석해 **항상 동일한 포맷**의 자립형(self-contained) HTML 보고서를 만든다. 특정 스키마에 의존하지 않는다.

## 핵심 원칙 — 왜 이렇게 하는가

LLM이 XML을 직접 읽고 매번 자유롭게 분석하면 (1) 뎁쓰(계층) 정보가 누락되고 (2) 파일마다/호출마다 포맷이 달라져 사용자가 결과를 신뢰할 수 없다. 그래서 역할을 엄격히 나눈다:

- **구조 추출, 계층 정리, 속성 수집, 통계, HTML 생성** → 전부 `scripts/Analyze-Xml.ps1`이 결정적으로 수행한다. 절대 직접 하지 않는다.
- **모델(너)의 역할은 두 가지뿐**: ① 스크립트 실행과 결과 안내, ② 보고서 마지막 "문서 해석" 섹션에 들어갈 요약문 작성.
- **생성된 HTML을 직접 수정하지 않는다.** 재실행하면 사라진다. 보고서를 바꾸고 싶으면 스크립트나 매핑(config/mapping.json)을 바꾼다.
- 보고서의 수치는 스크립트가 계산한 값만 사용한다. 네가 세거나 추정한 숫자를 쓰지 않는다.

## 실행 환경

- Windows + PowerShell 5.1 이상. 외부 모듈/인터넷 불필요.
- 실행이 막히면: `powershell -NoProfile -ExecutionPolicy Bypass -File <스크립트> ...`

## 워크플로

사용자가 `/xml-report <경로>` 형태로 호출하거나 파일을 @멘션하면 그 경로가 1단계의 `-Path` 인자다. 경로 없이 "xml 분석해줘"라고만 하면 대상 파일/폴더 경로를 먼저 확인한다. 별도 요청이 없어도 1~3단계(분석 → 요약 작성 → 요약 주입)를 기본으로 끝까지 수행한다.

### 1단계 — 분석 스크립트 실행

```
powershell -NoProfile -ExecutionPolicy Bypass -File "<스킬경로>\scripts\Analyze-Xml.ps1" -Path "<XML파일 또는 폴더>" -OutDir "<출력폴더>"
```

주요 파라미터:

| 파라미터 | 기본값 | 설명 |
|---|---|---|
| `-Path` | (필수) | XML 파일 하나 또는 폴더. 폴더면 내부 *.xml 전부 처리 |
| `-OutDir` | `.\xml-reports` | 보고서 출력 폴더 |
| `-Recurse` | 꺼짐 | 폴더의 하위 폴더까지 처리 |
| `-MappingPath` | `<스킬>\config\mapping.json` | 요소 라벨/문서유형/커넥션 매핑 파일 (도메인별 교체 가능) |
| `-SummaryFile` | 없음 | 3단계에서 사용. "문서 해석" 섹션에 주입할 텍스트 파일 |
| `-OpenDepth` | 3 | 트리에서 이 뎁쓰까지 펼쳐서 표시 |
| `-MaxTableRows` | 300 | 속성 상세 표의 요소별 최대 행 수(초과분은 표에 생략 건수 명시, 트리에는 전부 표시됨) |

파일마다 두 가지가 생성된다:

- `<이름>.report.html` — 완성된 보고서 (해석 섹션은 아직 placeholder)
- `<이름>.data.json` — 분석 다이제스트 (2단계에서 네가 읽을 파일)

폴더 처리 시 `index.html`(전체 목록)도 생성된다. 콘솔에는 파일별 통계와 **미분류 요소 목록**이 출력된다.

### 2단계 — 요약문 작성 (digest 기반)

`<이름>.data.json`을 읽고 "문서 해석" 요약문을 텍스트 파일로 작성한다(예: `<이름>.summary.txt`, UTF-8). 문단 구분은 빈 줄.

작성 규칙:

- **근거는 data.json만 사용한다.** 원본 XML 전체를 컨텍스트에 로드하지 않는다(대용량일 수 있고, 스크립트가 이미 전수 추출했으므로 다시 읽으면 편향과 낭비만 생긴다). 특정 값 확인이 꼭 필요하면 digest의 인스턴스 경로를 근거로 해당 부분만 확인한다.
- 수치는 digest의 값을 그대로 인용한다.
- 문서의 성격(무엇을 정의/기술하는 파일로 보이는지), 전체 규모, 계층 구성의 특징, 핵심 요소들, 연결 관계, 특이사항(비어있는 섹션, 미분류 요소 등) 순으로 5~12문장, 한국어로 쓴다.
- 확실하지 않은 해석에는 문장에 "…로 추정된다"를 명시한다. 이 섹션은 보고서에서 "모델 생성" 배지가 붙어 추출 데이터와 구분된다.

### 3단계 — 요약 주입 재실행

```
powershell -NoProfile -ExecutionPolicy Bypass -File "...\Analyze-Xml.ps1" -Path "<XML파일>" -OutDir "<출력폴더>" -SummaryFile "<이름>.summary.txt"
```

같은 입력이면 보고서는 해석 섹션만 채워진 동일 결과가 재생성된다(멱등). `-SummaryFile`은 단일 파일 처리에서만 유효하다. 여러 파일이면 파일별로 반복한다.

### 4단계 — 도메인 매핑 캘리브레이션 (선택, 반복 사용 시 권장)

같은 종류의 XML을 반복 분석한다면 도메인 매핑을 만들어 보고서 가독성을 높인다:

1. 보고서/콘솔의 **미분류 요소** 목록을 사용자에게 보여준다.
2. 사용자에게 각 요소의 한글 라벨(및 선택적 설명)을 확인받는다.
3. 확정된 것만 매핑 파일의 `labels`에 추가한다. 연결(참조) 성격의 요소면 `connectionNames`에, 연결의 출발/도착을 나타내는 속성명이면 `endpointAttrNames`에, 루트 요소명 키워드→문서유형은 `docTypes`에 추가한다.
4. 도메인이 여럿이면 `config/mapping.json`을 복사해 도메인별 파일(예: `mapping-배포설정.json`)을 만들고 `-MappingPath`로 지정한다. 보고서 상단 브랜드 문구도 매핑의 `brand` 키로 바꿀 수 있다.

**모르는 요소를 임의로 라벨링해서 매핑에 넣지 않는다** — 사용자 확인이 없으면 미분류로 남겨두는 것이 옳다(빠짐없이 표시는 되므로 정보 손실은 없다).

## 보고서 구성 (고정 포맷)

모든 보고서는 같은 순서의 섹션을 가진다: ① 파일 정보(SHA-256 해시 포함) → ② 검증 요약(파싱/렌더링 요소 수 일치 여부, 최대 뎁쓰, 속성 수 등) → ③ 계층 구조 트리(뎁쓰 배지, 접이식) → ④ 뎁쓰별 요소 요약 → ⑤ 요소별 속성 상세 → ⑥ 커넥션(연결 관계) → ⑦ 요소 인벤토리·매핑 상태 → ⑧ 문서 해석(모델 생성 배지). **모델의 해석/판단은 항상 마지막 섹션**이다 — 기계 추출 사실(1~7)을 먼저 보여주고 의견(8)을 뒤에 두어야 독자가 사실과 판단을 구분해 신뢰할 수 있다. 외부 리소스(CDN, 웹폰트) 없이 단일 파일로 열린다.

사용자에게 결과를 전달할 때는: 보고서 경로, 검증 요약 수치(요소 수/최대 뎁쓰/일치 여부), 미분류 요소 유무를 함께 알린다.

## 문제 해결

- **XML 파싱 실패**: 보고서 대신 콘솔과 index.html에 오류로 기록된다. 원인은 대개 잘못된 XML(태그 미닫힘)이거나 인코딩 선언 불일치. 파일 앞부분 몇 줄만 확인해 사용자에게 알린다. 임의로 파일을 고쳐서 재시도하지 않는다(원본 훼손 금지 — 사본을 만들어 고칠지는 사용자가 결정).
- **한글 깨짐**: XML 선언의 encoding과 실제 인코딩이 다른 경우다. 사용자에게 원본 인코딩을 확인한다.
- **보고서가 너무 클 때**: `-OpenDepth 1`로 트리를 접고, `-MaxTableRows`를 줄인다. 트리는 어떤 경우에도 전체 요소를 포함한다.
- **DTD 참조가 있는 XML**: 보안상 DTD/외부 엔티티는 무시하도록 설정되어 있다. 엔티티 치환이 필요한 파일이면 사용자와 상의한다.

## 파일 안내

- `scripts/Analyze-Xml.ps1` — 분석·보고서 생성 스크립트 (전부 여기서 수행)
- `config/mapping.json` — 라벨/문서유형/커넥션/브랜드 매핑 (기본은 범용 최소 설정, 도메인별 복제 가능)
- `assets/samples/` — 자가 테스트용 합성 샘플 XML

관련 스킬: AddSIM(국방 M&S) XML은 도메인 매핑·배경지식이 내장된 `addsim-xml-report`가 우선이다. 두 스킬은 동일한 분석 엔진을 공유한다.
